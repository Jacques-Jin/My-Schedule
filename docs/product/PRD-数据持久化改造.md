- 文档版本：v1.0

- 项目：我的日程（My Schedule）
- 优先级：🔴 高（阻塞产品可用性）

## 1. 问题陈述

### 1.1 用户反馈
"关闭网页后做出的一切修改都不会被保存"

### 1.2 根因分析

当前架构存在**两套独立的数据层**：

| 环境 | 存储方式 | 持久性 | 当前状态 |
|------|----------|--------|----------|
| 本地开发（`启动.bat`） | 内存假 Supabase（`FakeBuilder`） | ❌ 服务器重启即丢失 | 用户日常测试环境 |
| 生产部署（线上站点） | Supabase 云数据库 | ✅ 理论持久化 | runtime v30，v31–v41 未部署 |

**核心问题**：
1. 用户主要在本地开发环境测试，该环境**设计上就是临时存储**（用于开发调试）
2. 生产环境虽已部署，但版本滞后（v30 vs 本地 v41），且数据库状态未验证
3. 缺乏**离线优先**能力：无网络时无法使用，有网络时依赖云端往返

### 1.3 影响范围
- 用户体验：所有手动操作（添加日程、完成任务、修改设置）在重启后丢失
- 产品可用性：无法作为日常工具使用
- 后续规划：阻塞移动端 App / PWA 发布

## 3. 技术方案

### 3.1 方案选型

| 方案 | 描述 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **A. 纯 IndexedDB** | 浏览器本地数据库，完全离线 | 零延迟、隐私好、无需后端 | 不能跨设备同步、清缓存丢失 | ⭐⭐⭐ |
| **B. 纯 Supabase** | 保持现有云数据库架构 | 跨设备同步、数据安全 | 依赖网络、延迟高、本地开发不便 | ⭐⭐ |
| **C. 混合模式（推荐）** | IndexedDB 为主 + Supabase 云备份/同步 | 离线优先 + 云端同步、最佳体验 | 实现复杂度高、需解决冲突 | ⭐⭐⭐⭐⭐ |

**推荐方案：C. 混合模式（Offline-First with Cloud Sync）**

### 3.3 数据流

#### 3.3.1 读操作（Bootstrap）
```
1. 尝试从 IndexedDB 读取本地数据
2. 若本地有数据 → 立即渲染（离线可用）
3. 后台异步检查云端是否有更新
4. 若有更新 → 合并到本地 → 刷新 UI
```

#### 3.3.2 写操作（Save）
```
1. 写入 IndexedDB（立即生效，UI 乐观更新）
2. 将变更加入同步队列（Sync Queue）
3. 若在线 → 异步推送到 Supabase
4. 若离线 → 队列保留，联网后重试
```

#### 3.3.3 冲突解决策略
- **Last Write Wins (LWW)**：以时间戳最新的为准
- **字段级合并**：不同字段的修改可自动合并
- **用户提示**：严重冲突时弹窗让用户选择

### 3.4 技术选型

| 组件 | 技术 | 理由 |
|------|------|------|
| 本地存储 | **IndexedDB** (via `idb` 库) | 浏览器原生、大容量、结构化查询 |
| 同步队列 | 自实现（基于 IndexedDB） | 轻量、可控 |
| 云端 | **Supabase** (保持现有) | 已集成、无需改动后端 |
| 状态管理 | React Context + useReducer (保持现有) | 最小改动 |

## 6. 风险与缓解

| # | 风险 | 影响 | 概率 | 缓解措施 |
|---|------|------|------|----------|
| R1 | IndexedDB 配额不足 | 数据无法写入 | 低 | 监控配额，接近上限时提示清理 |
| R2 | 浏览器隐私模式禁用 IndexedDB | 应用不可用 | 中 | 降级到内存模式 + 提示用户 |
| R3 | 同步冲突频繁 | 用户体验差 | 低 | LWW + 字段级合并，严重冲突时提示 |
| R4 | 云端 Supabase 不可用 | 无法同步 | 低 | 离线优先，本地数据不丢失 |
| R5 | 数据迁移失败 | 用户数据丢失 | 中 | 迁移前备份，失败时回滚 |
