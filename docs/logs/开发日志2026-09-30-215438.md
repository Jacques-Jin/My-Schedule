## 1. 问题现象

战役详情中「拉入已有日程」勾选日程并确认后：

- 界面无任何变化（子计划列表仍为空、进度仍 0/0）；
- 刷新页面后依旧为空；
- 但网络面板中 `campaign.attach` 请求返回 **HTTP 200**，无任何报错。

即「请求成功但数据未落库、界面未更新」的静默失效。

---

## 2. 根因分析

**类型不匹配：DOM 字符串 id vs 存储层数字 id。**

勾选框渲染为 `<input type="checkbox" value={task.id} />`，DOM 的 `.value` 恒为**字符串**（`"1"`、`"2"`）；而 store 与数据库中的 task id 为**数字**（`1`、`2`）。确认时原代码直接取 `cb.value` 作为 id 数组下发，导致两端同时失效：

| 环节 | 代码位置 | 失效机理 |
|------|----------|----------|
| 客户端乐观更新 | `store.tsx` reducer `attach_tasks`：`action.taskIds.includes(t.id)` | `["1","2"].includes(1)` 为 `false` → 界面不更新 |
| 本地服务端 | `local-dev-index.ts` FakeBuilder `.eq("id", tid)` 用严格 `===` | `"1" === 1` 为 `false` → 匹配 0 行，更新 0 行，但仍返回 200 |
| 线上服务端 | PostgREST 会把 `'1'` 强制转换为整数 | 能落库，但客户端乐观更新仍失效（需手动刷新才可见） |

因此本地表现为「完全不生效」，线上表现为「生效但界面不即时刷新」——同一根因的两种表象。

---

## 3. 修复方案

在 DOM 字符串的**源头**（`CampaignsPage.tsx` 确认回调）把勾选值映射回 store 中真实的 id 类型，而不是在下游做字符串/数字猜测转换：

```tsx
onConfirm={() => {
  const checkboxes = document.querySelectorAll<HTMLInputElement>(".attach-task-check:checked");
  const checked = new Set(Array.from(checkboxes).map(cb => cb.value));
  // checkbox .value is always a string; map back to the store's real id type
  const ids = unattachedTasks.filter(t => checked.has(String(t.id))).map(t => t.id);
  if (ids.length > 0) handleAttachTasks(ids);
  else setAttachOpen(false);
}}
```

- `unattachedTasks` 即弹窗中渲染勾选框的同一批任务对象，用 `String(t.id)` 与 DOM 值比对后取回**原始 id**（数字），保证客户端 reducer 与服务端 payload 的 id 类型一致。
- 不改动 `handler.mjs` / `store.tsx`：二者逻辑本身正确，只是收到了错误类型的入参。

## 5. 顺带发现（本次未修，待确认）

战役详情中勾选**重复类**日程存在另一个独立 bug：`handleToggle` 传 `date: task.date` 且 `done: !task.done`，而重复任务的 `task.done` 恒为 `false`、完成态记录在 `task_completions`。后果是每次点击都向 `task_completions` 插入一条重复记录、勾选框永不显示选中、战役进度（按 `t.done` 统计）对重复任务永不变动。该问题与本次 attach 修复无关，已单独记录待用户确认是否修复。
