## 1. 改动概述

### 1.1 `src/lib/db.ts` — IndexedDB 封装层

使用 `idb` 库封装浏览器 IndexedDB，提供以下能力：

- **14 个 Object Store**：11 个数据表（与 Supabase 一一对应）+ `_sync_queue` + `_sync_meta`
- **cacheBootstrap(data)**：将 API bootstrap 响应批量写入 IndexedDB
- **loadFromCache()**：从 IndexedDB 读取全部数据（用于首次渲染）
- **put/putMany/remove/clearStore**：基础 CRUD
- **exportAllData/importAllData**：数据导出/导入
- **同步队列**：enqueueSync/getPendingSync/clearSyncQueue（Phase 2 使用）

### 1.2 `src/store.tsx` — 缓存优先 + 写穿同步

**Bootstrap 流程（refresh）**：
1. 先读 IndexedDB → 有数据则立即渲染（毫秒级）
2. 再调 API → 成功后更新 IndexedDB + 刷新 UI
3. API 失败但有缓存 → 保持缓存数据，不显示错误
4. API 失败且无缓存 → 显示错误

**写操作**：API 成功后同步写入 IndexedDB（write-through）
- save*：`api.xxxSave() → dispatch → db.put()`
- delete*：`api.xxxDelete() → db.remove()`
- completeTask：根据重复规则写入 tasks 或 task_completions
- batchTasks/attachTasks：API 成功后 refresh() 全量刷新缓存

**导出/导入**：
- exportData：优先从 IndexedDB 导出，fallback 到 API
- importData：先写 IndexedDB，再推 API，最后 refresh

## 3. 架构决策

### 3.1 为什么用 write-through 而非 write-behind？

- **Write-through**（本次采用）：写操作先调 API，成功后写 IndexedDB
  - 优点：实现简单，缓存与服务器始终一致
  - 缺点：写操作仍需网络

- **Write-behind**（Phase 2）：写操作先写 IndexedDB，异步推送 API
  - 优点：写操作零延迟，离线可写
  - 缺点：需要冲突解决、同步队列

Phase 1 先实现 write-through 确保数据持久化；Phase 2 再升级为 write-behind 实现完整离线写入。

### 3.2 为什么保留 API 调用？

IndexedDB 作为缓存层，API 仍作为权威数据源：
- 保证多标签页/多设备数据一致性（未来）
- 保留 Supabase 云端备份能力
- 不改变现有后端架构，最小化改动

### 3.3 settings 表的特殊处理

settings 在 Supabase 中是单例（id=1），IndexedDB 中以 `{ id: 1, ... }` 存储。bootstrap 返回的 `settings: [{...}]` 数组直接写入 IndexedDB。
